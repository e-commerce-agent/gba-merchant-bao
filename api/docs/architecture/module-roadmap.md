# 多人开发分工：业务技术模块与 Agent 接入条件

依据 [原始 PRD / 设计手稿（本目录入口）](README.md#initial-design) 和本次确认的分工整理。本文用于认领后续技术模块；下面的接口、表和 Service 是目标交付，不代表已经实现。当前已完成认证主体能力，auth 已调整为三层包结构；认证 change 的完整验收以其任务和测试报告为准。

Agent 基础已实现 LangChain4j 模型边界、本人会话六操作、start/token/done/error SSE、取消/超时和 MySQL 完整历史（V5）。2026-11-08 已完成真实兼容模型连通及真实认证 HTTP/SSE 自动化；Apifox 实际导入/协议验收仍待完成，不能据此宣称模块全部验收通过。证据见 [Agent 验收记录（本目录入口）](README.md#agent-verification)。以下 RAG、Function Calling、RabbitMQ、Redis ChatMemory、完整前端和真实 Nginx 集群仍是后续目标；citation/tool_call 只预留扩展语义，当前不发送这些事件。

## 1. 谁负责什么

| 技术模块 | 负责人 | 主要成果 |
| --- | --- | --- |
| 认证模块 auth | 已有实现，共同复用 | 消费者/员工登录、可信身份、租户/角色/本人资源授权、Redis 登录会话 |
| 商品模块 product | 队友认领 | 分类、商品/SPU、SKU、规格/兼容性属性、商户维护、公开商品查询 |
| 库存模块 inventory | 队友认领 | SKU 库存、受控调整、库存流水、公开可售状态查询 |
| 订单模块 order | 队友认领 | 消费者本人/商户范围订单查询、订单项成交快照、演示订单 |
| 物流模块 shipment | 队友认领 | 按已授权订单查询发货状态、承运商、运单与物流轨迹 |
| Agent 及配套 | 你负责 | 知识库/文档、RAG、Function Calling、RabbitMQ 异步文档任务、聊天历史/SSE、Redis ChatMemory、Agent 评测 |

这四个队友模块是可独立认领的工作单元，不规定必须四个人一人一个。人数不足时可由同一人负责多个，仍按模块交付。你无需负责开发他们的商品/库存/订单/物流 CRUD；他们也不需要替你写 Tool、Prompt、向量检索或 ChatMemory。

最终要演示：商户上传说明书、SKU 兼容性资料、售后政策和店铺规则，消费者/客服向 Agent 提问；Agent 按可见范围检索知识；实时订单/库存/物流交给只读 Tool；批量 PDF/Word/Markdown 异步解析、切分、Embedding、Milvus 写入，有进度、部分失败、重试/死信/人工重投；连续追问由 ChatMemory 与完整历史支撑。

消费者和客服只能访问授权范围内的知识，商户内部资料不得因“已登录”直接暴露给消费者；匿名只允许公开商品/库存状态及公开知识问答。客服可向 Agent 提问，但接管消费者会话、人工回复、恢复 Agent 不作为本次验收目标。

## 2. 商品技术模块（队友认领）

**负责什么：** 管理 3C 商品及其可售规格，并为商城和 Agent 提供商品事实。

| 交付项 | 具体内容 |
| --- | --- |
| 功能 | 本商户分类、商品新增/修改/上下架、SKU 与规格属性维护；公开列表/详情只显示已发布内容；员工查询本商户管理数据 |
| 数据 | 按 PRD 设计 product_category、product、product_sku、product_attribute 等表及关系；兼容型号、接口、功率、颜色、长度、插头等结构化字段；最终字段/索引在本模块 change 冻结 |
| HTTP 接口 | 公开店铺商品列表/详情、SKU 详情；员工本商户维护接口。当前整合契约为 `/api/v1/stores/{storeSlug}/products`、`/products/{productId}`、`/skus/{skuId}`（后两项同一店铺基路径），登录读取/维护为 `/api/v1/products`、`/api/v1/skus/{skuId}`；详见商品模块文档和 `align-commerce-module-integration` 第 4 节 |
| 给 Agent 的能力 | 商品检索、商品详情、SKU 规格与兼容性查询的 Service，返回名称、规格、状态等必要字段；建议命名 ProductQueryService，最终以真实实现为准 |
| 测试/演示 | 充电器、数据线、耳机及多 SKU；两个商户隔离；停售/未发布商品不可公开；非法 SKU/跨商户访问拒绝 |

**什么时候够你接 Agent：** 商品/SKU 的真实查询 Service 已能按商户和可见范围查数据、测试通过，就可以做商品 Tool；不必等员工所有维护接口和前端页面全部完成。知识库也可以先上传独立文档，不必等商品表完成。

## 3. 库存技术模块（队友认领）

**负责什么：** 回答“这个 SKU 有没有货”，让员工能受控维护库存。

| 交付项 | 具体内容 |
| --- | --- |
| 功能 | SKU 库存初始化、受控调整、调整原因/流水、可售状态查询；并发更新与重复调整有处理规则 |
| 数据 | inventory、inventory_transaction；关联本商户 SKU；可售数量按 on_hand - reserved 等本模块冻结的规则计算，不能出现非法负库存；version/幂等约束在设计中明确 |
| HTTP 接口 | `/api/v1/skus/{skuId}/availability` 等消费者查询，以及本商户员工库存查询/调整接口；消费者只获得公开可售信息 |
| 给 Agent 的能力 | 查询 SKU 是否可售及必要状态的 Service，建议命名 InventoryQueryService；库存数量/管理流水不直接交给消费者 Tool |
| 测试/演示 | 有货、缺货、停售 SKU；并发调整、幂等、跨租户拒绝；库存计算边界 |

**依赖谁：** 需要商品模块的 SKU 标识、商户归属和状态。可与商品模块同时开始需求、表结构和代码开发，集成时用真实 SKU。

**什么时候够你接 Agent：** 按租户/SKU 查询可售状态的真实 Service 可用，就能接库存 Tool；不必等库存管理页面完成。首期不因库存模块额外建设消费者下单、支付、扣减/释放交易链路。

## 4. 订单技术模块（队友认领）

**负责什么：** 让消费者查询自己已有的订单，让员工查询本商户订单。

| 交付项 | 具体内容 |
| --- | --- |
| 功能 | 本人订单列表/详情、订单项、订单状态；员工本商户查询；订单按 dev 种子提供即可，本期不强制建设后台录单功能 |
| 数据 | orders、order_item；订单关联商户与消费者；订单项保存名称、SKU 属性、成交价格和数量快照，不依赖当前商品详情重建历史 |
| HTTP 接口 | `GET /api/v1/orders`、`GET /api/v1/orders/{orderId}`；不同主体在 Service 和 SQL 中限制各自范围 |
| 给 Agent 的能力 | 从可信 Actor 查询本人订单列表/详情的 Service，建议命名 OrderQueryService；对 Tool 返回状态、商品快照等必要字段，去除手机号、地址等隐私 |
| 测试/演示 | 待发货、运输中、已完成、已取消订单；两租户、多消费者；同租户他人订单/跨租户/不存在均不泄露存在性；商品变更不影响成交快照 |

**依赖谁：** 认证提供消费者身份，商品模块提供 SKU/商品信息。订单查询不依赖库存调整接口，也不需要下单/支付/扣库存能力。

**什么时候够你接 Agent：** 真实 Service 能验证租户与消费者归属并返回订单信息，就能接订单 Tool。用户或模型提供订单号只是筛选条件，不能替代授权；不能接受它们自报的 merchantId/customerId。

## 5. 物流技术模块（队友认领）

**负责什么：** 基于用户有权查看的订单，返回是否发货、承运商和最新物流轨迹。

| 交付项 | 具体内容 |
| --- | --- |
| 功能 | 按订单查询未发货/运输中/已签收状态、承运商、轨迹；只有数据提供时才返回预计送达，不编造时间 |
| 数据 | shipment、shipment_track；关联同商户订单、记录事件时间和轨迹；dev 种子提供物流数据，不要求真实物流平台 SDK |
| HTTP 接口 | `GET /api/v1/orders/{orderId}/shipment`；先验证订单归属，再查物流 |
| 给 Agent 的能力 | 查询当前主体有权访问的订单物流的 Service，建议命名 ShipmentQueryService；返回脱敏状态与轨迹摘要 |
| 测试/演示 | 未发货、多段运输轨迹、已签收；订单越权拒绝；不能凭 trackingNo 绕过本人订单授权 |

**依赖谁：** 订单模块的真实归属查询和稳定订单标识。物流负责人可提前实现自己的表/查询代码，最终验收须接真实订单授权。

**什么时候够你接 Agent：** 已授权订单能通过真实 Service 查物流时，就接物流 Tool；其他物流后台能力不阻塞这一步。

## 6. 你负责的 Agent，具体拆成哪些开发任务

以下是你内部的开发拆分，不再分给队友。每部分可按实际工作量建立独立 change，不必一次实现全部目标表。

| 你的开发部分 | 具体要做什么 | 外部前置 |
| --- | --- | --- |
| Agent 基础与对话接口 | LangChain4j 模型调用、Prompt、消费者/客服问答入口、SSE token/citation/tool_call/done/error 事件、断开取消、超时和错误处理 | 已有认证；公开入口另定义店铺范围、白名单和限流 |
| 知识库与 RAG | 知识库/文档元数据、原文件存储、说明书/兼容性/政策上传、格式/大小校验、版本/可见性、解析切分、Embedding、Milvus 检索、引用、无答案处理 | 认证与商户范围；你自己的文件/解析/模型链路，不等待商品管理完成 |
| Function Calling | 为就绪业务 Service 编写只读 Tool；模型参数校验、可信身份注入、脱敏、超时/有限重试/降级、调用记录 | 对应商品/库存/订单/物流的真实查询 Service；每个 Tool 分别接入 |
| RabbitMQ 异步文档任务 | 批量上传后返回 taskId；把解析→切分→Embedding→Milvus 写入放入任务；MySQL task/item 进度与幂等；确认/ACK、部分成功、失败重试、死信、人工重投与补偿 | 你自己的文档管理和可执行处理阶段；不依赖四个电商查询模块或 FC |
| 会话历史与 Redis ChatMemory | 创建/查询本人会话、MySQL 完整消息/引用/Tool 摘要、消费者/客服发送者归属；Redis 窗口/摘要、token 预算、TTL、过期历史恢复、并发控制 | 认证 + 你自己的基础问答链；不等待 RAG/FC/MQ 全部完成 |
| 评测与交付 | 用例/配置版本、真实运行结果、badcase；RAG 引用/隔离、Tool 归属/故障、MQ 重试/幂等、Memory 多轮/恢复；导出 OpenAPI 供前端开发 | 随各能力完成进行，不单独交给队友当一个笼统“评测模块” |

Agent 配套目标表按需加入：知识库/文档/切片；document_task/document_task_item；chat_session/chat_message 与引用/Tool 记录；评测结果等。MySQL 保存完整历史和业务任务状态，Redis 不是唯一历史来源，RabbitMQ 队列不是唯一任务状态来源。

上传 HTTP 请求负责校验并可靠保存原文件及任务信息，耗时解析、切分、Embedding 和 Milvus 写入异步执行；不让后台消费者依赖已经结束的上传请求临时流。上传返回 202、taskId/statusUrl，任务查询显示每个文档结果与总进度，失败文档可单独重试。多文件接收方式、持久化后可靠投递和补偿细节在对应 change 冻结。

## 7. 认证之后，大家实际怎么并行

1. **队友同时开工：** 分别认领商品、库存、订单、物流。商品负责人优先稳定 SKU；库存/订单负责人可以同时开发，物流负责人可同时准备轨迹与查询。最终集成有 SKU→库存、SKU→订单→物流依赖，不要求上游整模块全部做完才开始自己的工作。
2. **你同时开工：** 搭基础 Agent/问答入口，开发知识文档和 RAG；文档处理阶段可用后接 RabbitMQ；完整历史和基础对话可用后接 ChatMemory。这些不必等待队友的商品/订单接口。
3. **业务查询够用就接：** 商品查询能用了，接商品 Tool；库存查询能用了，接库存 Tool；订单/物流同理。以真实 Service、授权和必要结果字段可用为接入条件，不等四个模块全部完工，也不强制先制定一套测试替身对接流程。
4. **逐项联调验收：** 对应队友与你一起验证真实数据、授权失败、依赖故障；有接口/字段变化时同步调用方。前端通过导出的 OpenAPI 开发，Agent 调用 Java Service，不通过 HTTP 回调本应用。

```text
认证（已有）
  ├─ 队友：商品 ──┬─ 库存 ───────────────→ 你的库存 Tool
  │              └─ 订单 ── 物流 ───────→ 你的订单 / 物流 Tool
  │       └────────────────────────────→ 你的商品 Tool
  └─ 你：Agent 基础
           ├─ 知识库 / 文档 / RAG ──→ MQ 异步导入
           └─ MySQL 完整历史 ──────→ Redis ChatMemory
```

图中 MQ 复用文档处理阶段，不表示必须先完成全部 RAG 问答才能写任务调度；完整异步导入验收必须跑真实解析、切分、Embedding 和 Milvus 写入。RAG、FC、MQ、ChatMemory 没有必须依次完成的强制链。

## 8. 所有人的统一交付标准与三层包结构

每位模块负责人都交付自己的需求/验收、API 契约、表/索引/Flyway、完整后端代码、测试、dev 演示数据、维护文档及导出的 OpenAPI。只写一个 Controller 或只建表不算模块完成。目标业务按本文收口：订单/物流只读，也要交付完整查询模块及授权、测试，不扩展到消费者下单支付。

```text
com.gba.merchantbao/
  auth/                 已有认证，已按下列结构整理
  product/              队友的商品模块
  inventory/            队友的库存模块
  order/                队友的订单模块
  shipment/             队友的物流模块
  agent/ knowledge/ chat/ 等按 Agent 实际职责建立
    controller/         HTTP / SSE 入口
    service/            业务编排、授权、事务与跨模块调用
    mapper/             MyBatis / SQL
    entity/             数据库模型
    dto/                输入
    vo/                 独立输出模型，按需要建立
    config/ 等          按需要建立辅助包
```

每个实际业务包都采用 controller/service/mapper；不再以 api/application/domain/infrastructure 作为业务分层目录。MyBatis 使用 mapper 命名，不同时建立 dao 同义包。辅助职责如 auth 的 security/cache/handler/util 按需保留；不预建空包，不机械添加没有差异的接口/impl。

Controller 不直接访问 Mapper；Service 与 SQL 同时执行租户/本人范围限制；身份只来自认证 Actor（公开入口由店铺解析）。模型输出或请求中即使包含 customerId、merchantId、订单号也不能绕过授权。匿名不得访问私有 Tool、订单、物流和持久化历史。

Flyway 版本和 devdata 编号由团队协调，已发布迁移不修改。dev 演示数据与 test fixture 分离，自动测试使用隔离容器，不操作 gba-dev 业务卷。对象存储、Milvus、RabbitMQ 等按首次实际使用的模块接入；CI、真实短信、生产开通/部署、课程 WebService/Nginx/并发验证另行规划。

本文不安排消费者下单/支付、订单超时 MQ、复杂 RBAC、平台后台或客服接管。原 PRD 中这些扩展目标不作为本次四亮点及 ChatMemory 的前置。当前认证白名单也不会因本文自动开放未来的公开商城/Agent 接口。
