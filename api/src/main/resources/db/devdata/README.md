# dev 演示业务数据

只由 dev 加载，不进入 test/prod 的迁移 locations。
设计手稿约定一个 3C 样板租户 M_3C_DEMO 和一个最小隔离对照租户 M_ISOLATION_TEST；
二者的租户根位于 db/seed/nonprod，不在此重复创建。

后续按模块增量提供幂等演示数据：商品模块负责充电器、数据线、耳机及 SKU；
库存模块负责可售数量；订单模块负责订单及订单项快照；物流模块负责运单和轨迹；
知识/RAG 模块负责公开及私有知识；会话模块负责最小会话与消息。
未实现模块不预建表，不将旧餐饮数据冒充上述样板数据。V1–V5 与 R010/R020/R030 是已执行基线，保持内容不变；V6–V9 按商品、库存、订单、物流顺序创建。
用例需要的数据单独放 src/test/resources/db/fixture，由 @Sql 显式加载。

R__020_auth_demo_accounts.sql 仅在 dev 提供两个租户首员工和三个消费者，稳定用户名/手机号缺失才插入，不重置 hash/status。开发密码与联调步骤见 [认证文档入口](../../../../../docs/auth/README.md)；生产开通延期。普通 test 不加载，AuthDevManualIT 仅在独立临时基础设施显式模拟 dev 加载。

租户与账号仅补缺失记录，保留人工名称/状态/密码等资料；预期租户缺失或稳定身份冲突时通过 `dev_seed_*` 校验明确失败。R 首次或校验和变化才执行，上游变化不自动触发下游；手工删除数据后重启不自动补回。补种须显式受控执行，不改 history。
## 初始化顺序

先执行所有待执行 V，再按 R 描述的三位数字前缀排序：nonprod 的 `R__010_local_test_tenants.sql` → devdata 的 `R__020_auth_demo_accounts.sql` → `R__030_chat_demo.sql` → `R__040_product_demo.sql` → `R__050_inventory_demo.sql` → `R__060_order_demo_orders.sql` → `R__070_shipment_demo_data.sql`。locations 顺序不表达依赖，不使用 AFTER_MIGRATE 回调或启动补写。

| V | 结构 | R | 业务依赖 |
| --- | --- | --- | --- |
| V1–V5 | 冻结的旧基线、租户、认证、会话结构 | R010–R030 | 内容及 SHA-256 不变 |
| V6 | 商品分类、商品、SKU、属性 | R040 商品目录 | 两个租户 |
| V7 | SKU 库存、库存流水、幂等表 | R050 库存 | R040 SKU |
| V8 | 订单、订单项成交快照 | R060 订单 | 账号及 R040 商品/SKU |
| V9 | 运单、物流轨迹 | R070 物流 | R060 订单 |

只重排当前本地 dev V5 之后尚未执行的 V6–V9；其他旧 V6–V9 编号布局不兼容，维护工具会拒绝。test/prod 不加载 R040–R070，且新结构迁移不读取 R 种子。

R030 提供四个本人会话（同商户两个消费者、一个员工、另一商户消费者），每个会话一轮静态演示问答，不表示已接入真实模型。会话 ID 为 2200000000000001–4，消息 ID 为 2300000000000001–8，run ID 为 2400000000000001–4，账号沿用 R020。只补缺失记录，不覆盖人工内容、状态或运行信息；缺账号/商户、固定 ID 归属或消息序号/幂等键/run 标识冲突时明确失败。详见 [Agent 文档入口](../../../../../docs/agent/README.md)。

R040 提供两租户商品目录演示数据：分类/商品/SKU/属性 ID 分别为 2500000000000101–105、2500000000000201–206、2500000000000301–309、2500000000000401–408。包含多规格、停售 SKU、未发布/草稿商品和隔离租户对照商品。只补缺失记录，保留人工字段；固定 ID、自然键及归属冲突在写入前明确失败。
分类先用独立语句插入根分类，再插入子分类，保证逐行外键检查时父记录已存在；不依赖 `UNION ALL` 的书写顺序或 JOIN 执行计划。商户统计信息刷新后的 hash join 场景纳入种子回归测试。

R050 为 8 个真实目录 SKU 初始化库存，包含两商户有货、零可售、预占量和停售 SKU 保留库存。固定库存 ID 为 `2500000000000501–507/509`，分别对应 SKU `2500000000000301–307/309`；508 保留不用。固定 ID 被其他商户/SKU 占用，或预期商户/SKU 已对应其他 ID 时，在任何库存写入前以 `dev_seed_inventory_identity_conflict` 失败。重跑仅补缺失行，不覆盖人工数量/version，不创建库存流水或幂等记录。

库存三表主键均为无默认值、无 AUTO_INCREMENT 的 BIGINT。业务运行时由现有单例 `common.id.IdGenerator` 生成雪花 ID；SQL seed/fixture 显式固定 ID 是可复现数据约定，不在 SQL 内实现雪花。`db/fixture/inventory.sql` 使用独立测试库存 ID `2600000000000501/503`（对应测试 SKU 301/303）；测试流水保留 `26000000000006xx`，注入生成器验证值使用 `270...`。这些范围不修改已有商品、SKU、订单或物流标识，也不要求运行时 ID 连续。

R060 提供 M_3C_DEMO 六单和 M_ISOLATION_TEST 一单，8 条订单项引用 R040 中同商户且属于对应商品的 SKU；订单总额等于订单项金额合计，成交名称/规格/价格保留在历史快照中。稳定订单 ID 为 2100000000000301–0307，订单项 ID 为 2100000000000311–0318。

R070 提供 M_3C_DEMO 两张运单及 M_ISOLATION_TEST 一张运单，order_id/order_no 和商户归属匹配 R060 订单；IN_TRANSIT 运单对应 SHIPPED 订单。物流联调步骤见 [物流文档入口](../../../../../docs/shipment/README.md)。NOT_SHIPPED 由服务在无运单记录时合成。

## 受控补种

1. 停止后端和相关写入，核对目标库、当前新 V/R 布局；备份结构、数据和 history，并在隔离实例恢复验证。
2. 核对待补行的父记录、稳定 ID、自然键及商户归属；选择实际需要补缺的脚本，按 R040 → R050 → R060 → R070 的依赖顺序在受控 SQL 连接中显式执行。租户和账号须已存在，guard 报错时停止调查。
3. 核对新增行及同商户关系，确认已有快照、库存数量/version、账号和会话未变；不手工登记 Flyway 成功、不删除或改写 history、不自动 repair。普通重启仅 migrate/validate，不强制补种。

旧名 R 的专用历史升级另见下方维护说明；正常编号的 V5 dev 库不需要通过该工具补种。

旧名已执行库按 [运行与部署文档入口](../../../../../docs/deployment/README.md) 先完成一次性受控升级；不保留运行期兼容空脚本，不自动 repair，不混跑旧迁移包，不删除卷。生产只加载 migration/common，不执行开发种子改名 repair。
