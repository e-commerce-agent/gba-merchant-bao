更新时间：2026-10-06

本文记录 `refactor-foundation-stack-and-migrations` 实施前的可复核事实。备份文件和数据库凭据只保存在本机临时目录，不提交 Git。

| 项目 | 当前事实 |

| Maven 工程 | `api/merchant-common`、`api/merchant-pojo`、`api/merchant-server` 三模块 |

目标工程改为按业务域分包的单 Maven 应用，但旧模块和旧接口先作为兼容输入保留，迁移完成前不静默删除。

## 2. 旧库核对

应用开发配置指向本机 MySQL 的 `sky_take_out`。本次只读核对结果：

- 表数量：11
- 表：`address_book`、`category`、`dish`、`dish_flavor`、`employee`、`order_detail`、`orders`、`setmeal`、`setmeal_dish`、`shopping_cart`、`user`
- 已生成完整数据备份和无数据结构备份到本机临时目录 `electricbusiness-migration-baseline`。
- 完整备份已导入临时数据库 `electricbusiness_migration_check`，恢复后仍为 11 张表，随后删除临时校验库。
- 原 `sky_take_out` 数据库只执行查询和 `mysqldump`，未执行 `DROP`、`ALTER`、`UPDATE` 或 `DELETE`。

备份恢复命令和结果由执行终端记录保留；正式 Flyway V1 仍须以该真实库的结构导出为来源，并移除无条件删除语句和演示数据。

## 3. 固定租户和测试夹具契约

基础迁移只建立 `merchant` 租户根表，并在 `local/test` 种入以下两个业务编码：

| 业务编码 | 用途 | 允许数据 |
|---|---|---|
| `M_3C_DEMO` | 3C 配件样板租户 | 后续商品、SKU、库存、订单、物流、知识和会话固定数据的归属 |
| `M_ISOLATION_TEST` | 最小对照租户 | 专门验证跨租户读取、更新、删除、Tool 和 SSE 越权 |

固定夹具规则：

1. 业务编码是跨 Flyway、Testcontainers、Apifox 和后续评测引用的稳定入口；测试不得硬编码每次变化的自增或 Snowflake 数字 ID。
2. 本基础 change 不创建登录账号、商品、订单、物流、知识或会话数据；这些数据随对应技术模块以幂等种子追加。
3. 每个后续模块必须登记数据编码、`merchant_id` 归属、预期状态和跨租户失败场景；不得改写已经发布的夹具编码。
4. 生产 profile 不加载 `db/devdata`，生产只执行结构迁移和必要的数据映射。

## 4. 基础 schema 不变量

- 商户私有表必须有非空 `merchant_id`；平台级表必须显式标注为非租户表。
- 唯一约束和高频查询索引以 `merchant_id` 为首列；更新和删除 SQL 同样必须带服务端身份解析出的租户条件。
- 需要数据库引用约束时，优先使用包含 `merchant_id` 的组合关系，避免仅凭全局资源 ID 建立跨租户引用。
- 主键生成策略统一；对外只使用不透明业务编码或字符串化 ID，不让前端依赖数字 ID 精度。
- 公共字段按实际用途使用 `created_at`、`updated_at`、`created_by`、`updated_by`、`version`；订单、库存流水、消息等审计数据不随意增加逻辑删除。
- 金额使用 `DECIMAL(12,2)` 和明确币种；库存使用整数；时间统一项目时区或 UTC，并在接口层说明。
- 状态使用有明确含义的字符串/枚举，不使用没有字典的魔法数字。
- 手机号保存规范化原值用于匹配和唯一约束；响应、日志和审计输出使用 `maskPhone`，`phone_masked` 不作为登录字段或唯一键。

## 5. 验收证据

- 旧库只读备份可恢复到隔离库。
- 空库路径：执行 V1 和基础租户种子后得到 `M_3C_DEMO`、`M_ISOLATION_TEST` 两行。
- 已有库路径：结构核对通过后才允许 baseline；结构不匹配必须失败并保留原因。
- 后续版本不得修改已执行的 V 文件，只能追加新版本；所有模块测试按业务编码解析租户主键。
