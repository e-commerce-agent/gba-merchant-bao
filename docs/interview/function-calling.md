# Agent Function Calling 面试卡片

更新：2026-11-15。实现由 [PR #29](https://github.com/e-commerce-agent/gba-merchant-bao/pull/29) 合入。本文聚焦工具调用流程、轮次边界、Actor 授权与数据隐私；Agent 基础 SSE 生命周期见 [agent.md](agent.md)，RAG 检索见 [rag.md](rag.md)。

## 一、业务梳理

消费者或商户员工在 Agent 对话中询问实时订单状态时，模型可以判断是否需要查询订单。系统必须把“模型提出工具请求”和“服务端有权读取订单”分开：模型只提交订单号，服务端按当前登录身份与商户边界查询，再将有限结果交回模型生成自然语言回答。消费者只能查询本人订单，员工只能查询本商户订单；工具调用不新增对外 HTTP API。

可直接讲的开场：

> 我在原有 SSE 对话和 RAG 检索流程上增加了只读订单 Function Calling。一条用户消息仍然只创建一个 run：先提交运行权并执行 RAG，再让模型最多用一次非流式请求选择工具；服务端以可信 Actor 查询订单，最后最多再调用一次不带工具定义的模型请求，通过原 SSE 输出正文。正文、RAG 来源和封闭工具摘要在终态事务中一起提交。

## 二、技术实现

**流程位置：** 基础 Agent 在 run 获得 MySQL 运行权后调用模型并直接流式输出。RAG 接入后，检索成为模型上下文准备步骤。Function Calling 位于 RAG 上下文准备之后、最终正文 SSE 之前：首个模型请求允许 `lookup_order`；如果模型请求工具，服务端最多执行一次查询并把 assistant tool-call 与 tool result 加入本轮上下文，然后发起最终模型请求；最终模型请求不再声明 tools，统一流式输出正文。如果首个模型请求直接完成而未请求工具，就直接结束本轮，不再发起第二次模型请求。RAG 无匹配时仍保留原问题进入模型请求；检索依赖失败则按错误终止。

**轮次定义：** 一条用户消息、一组 USER/ASSISTANT 持久化消息和一个 `runId` 构成一个业务轮次。轮次不按模型 API 调用数计算。一轮最多两次模型请求、一次工具执行：首个模型请求若直接完成，则本轮只有这一次请求；若请求工具，则服务端执行工具后最多再发起一次不带工具定义的流式模型请求。工具往返是服务端内部协议上下文，不单独产生用户消息或 SSE 事件。

**终态：** 最终正文、RAG `sources`、最多一个固定工具名/状态组成的 `toolCalls` 摘要，与运行权释放在同一终态事务提交。提交成功后才发送原有 `done`；历史接口读取相同摘要。未调用工具、失败、取消、超时等没有成功摘要时返回空数组。

**授权和隐私：** 工具 schema 只开放 `lookup_order(orderNo)`。适配器只接受白名单工具，解析 JSON 对象并校验必需字段、格式和长度；拒绝未知工具、畸形参数、多个调用和二次工具调用。`AgentOrderLookup` 使用从认证上下文显式传过异步边界的可信 `Actor` 调用订单领域服务。模型不能提供或覆盖商户、账号、角色等身份字段。消费者查询限定当前商户及本人 `customerId`；员工查询限定当前商户。跨商户、他人及不存在的订单不可见，不会把结果交回模型。

协议参数和原始订单结果只在服务端本轮工具往返中使用。MySQL 的 `tool_calls_json`、SSE done 和历史只记录固定工具名与状态，不保存订单号、原始参数、订单响应、地址或联系方式。工具摘要证明发生过调用，不证明回答内容正确。

**数据流：** Bearer → 认证过滤器得到可信 Actor → `ChatController` 校验请求 → `ChatService#accept` 校验归属/幂等并在事务内取得运行权、保存用户消息和助手占位 → 有界执行器执行 RAG 检索并准备上下文组装 → 首次模型请求允许 `lookup_order`；若请求工具，则由 `AgentOrderLookup#query` 以可信 Actor 调用订单服务，再将 assistant tool-call 与 tool result 加入本轮上下文并进行最终流式模型调用；若未请求工具tools，则首次模型调用结束本轮 → `ChatRunExecution` 在同一终态事务提交正文、RAG sources、工具摘要并释放运行权 → 发送 SSE done/error。每条用户消息仍是一轮、一个 run；模型调用最多两次，订单工具最多执行一次。客户端断开后通过本人历史接口查询，不承诺 SSE 重放或跨实例恢复生成。

## 三、技术深挖：两个主讲难点

### 难点一：工具调用插在 SSE 与 RAG 的哪里？怎么算一轮？

Function Calling 不替换已有的 SSE 生命周期，也不把工具选择当成新一轮。RAG 先根据原问题准备来源和上下文；随后首个非流式模型调用决定是否请求工具。若模型请求工具，应用执行至多一次授权查询并续接协议消息，再由最终模型调用生成正文；若首个模型调用直接完成，则本轮在该调用结束，不会再发起最终模型请求。无论 RAG 是否命中，原问题都会进入首个模型请求；检索依赖错误仍按失败终止。

因此一条用户消息仍是一轮、一个 `runId`，只是内部最多包含两次模型 API 调用和一次工具调用。SSE 客户端只接收最终正文与 `done` 中的 RAG 来源、封闭工具摘要，不会看到工具参数和原始订单响应。终态事务提交后才发 `done`，重试、断线和历史读取继续沿用原有 run 状态语义。

面试话术：

> 我按用户消息和持久化 run 定义轮次，而不是按模型请求次数定义。一轮先完成 RAG，再用最多一次带工具定义的非流式请求作工具选择；服务端最多查一次订单，然后用最多一次不带 tools 的模型请求统一 SSE 输出最终正文。工具协议消息只是这轮内部上下文。正文、来源和工具摘要同事务提交后才发 done，所以没有引入第二个用户轮次或新的 SSE 事件。

### 难点二：模型自主选择工具，怎么防止乱查和泄露隐私？

模型只能提出白名单中的订单号查询，不持有数据库能力。服务端校验工具名和参数后，以认证时产生的可信 Actor 调用既有订单授权服务；Actor 显式传入异步 run，避免依赖已清理的线程上下文。消费者限定本人及当前商户，员工限定当前商户。模型不能选择身份、扩大商户范围或切换角色；越权和不存在统一不可见。

工具参数及原始订单数据只留在服务端本轮内存并用于生成。持久化摘要只包含固定工具名和非敏感状态，SSE 和历史不暴露订单号、工具参数或订单原始数据。安全边界由白名单、结构校验和领域服务授权共同实施，不依赖提示词要求模型自律。

面试话术：

> 我把模型的工具选择权和数据访问权分开。模型能提出 `lookup_order(orderNo)`，但查库由服务端完成。服务端校验参数后把可信 Actor 传给订单领域服务，消费者仅能查本人、员工仅能查本商户；跨租户和越权结果不可见。订单结果只供当前回答使用，落库只存固定工具名和状态摘要，不存参数和原始响应。

## 四、高频八股

| 追问 | 项目回答 |
| --- | --- |
| 为什么需要两次模型请求？ | 第一次只在模型要求时返回结构化工具调用；应用执行授权查询后，第二次把 tool result 交回模型生成最终回答。每轮有界为最多两次模型请求、一次工具执行。 |
| 工具调用为什么不直接做成 HTTP API？ | 它是登录聊天运行内部能力，不需要扩大外部接口面。服务端使用当前 Actor 执行，客户端和模型都不能自行指定授权身份。 |
| 消费者如何避免查到他人订单？ | 从已认证 Actor 取得 account/customer 与 merchant 范围，订单服务查询同时约束商户和本人 customerId；跨商户、他人和不存在不可见。 |
| 工具摘要为什么不存完整输入输出？ | 聊天历史只需说明调用了哪项工具及结果状态。订单号、参数和订单详情可能含隐私，不进入摘要、SSE 或历史。 |
| 无 RAG 结果是否直接回答资料不足？ | 否。无匹配仍把原问题交给模型并允许工具选择；RAG 依赖故障才以依赖错误结束。 |
| `toolCalls` 能证明回答正确吗？ | 不能。它仅证明工具执行摘要，回答正确性仍需单独评估。本次自动化测试验证协议、授权与一致性，不评价真实模型工具选择准确率。 |
