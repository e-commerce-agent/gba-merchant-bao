# Design

## Context

见 proposal.md 的 Why。当前 `AgentModel` 只转发文本 delta 和最终用量；`ChatService.execute` 在持久化运行权后执行 RAG，再调用流式模型。`ChatRunExecution` 负责收集正文、事务提交终态并送出 SSE。`OrderQueryService.detail(Actor, orderId)` 已实现按可信 Actor 授权的订单详情查询；订单号在现有数据库中由商户唯一约束。

现有 RAG 无匹配时会直接将“资料不足”作为成功回答完成，不调用生成模型。Function Calling 接入后，无匹配必须保留原问题进入模型，让模型判断是否查询订单。RAG 检索依赖故障仍按错误终止。

## Goals / Non-Goals

**Goals:**
- 沿用现有 SSE 与聊天运行生命周期，在模型回合之间执行一个只读、授权的订单号查询。
- 保证模型工具协议内容留在服务端，并让终态回答和工具摘要原子持久化。
- 不改变既有 RAG 来源快照、身份授权和完整 MySQL 聊天历史职责。

**Non-Goals:**
- 不增加 Tool HTTP endpoint、通用工具注册平台、任意 SQL/API 工具、多个工具、多次工具循环、写操作、MCP 或多 Agent。
- 不引入 RabbitMQ 上传/批量处理、Redis ChatMemory、匿名对话或订单新业务表。
- 不将模型选择的工具调用逐项作为 SSE 事件发送；前端仍只消费既有事件类型。

## Decisions

### 订单号查询使用现有订单领域服务和可信 Actor

模型只接收一个 `orderNo` 字符串参数，长度不超过数据库列上限并满足字符格式。聊天服务从已认证会话执行上下文取得 Actor；不接受客户端或模型提供的 merchantId、accountId、role。订单领域服务新增按订单号的 Actor 查询入口：员工只能查询本商户订单，消费者只能查询本商户且 customerId 为本人的订单。跨租户、不属于本人及不存在统一视为不可见；详情及商品快照仍由现有订单查询服务返回。

考虑过直接把订单查询 HTTP API 暴露给模型或以 merchantId 调用 `locateForService`，但这会扩展外部接口或绕过消费者本人授权，因此不采用。

### 模型适配器返回结构化工具请求，聊天运行协调一次往返

Agent 模型边界扩展为可声明当前轮允许的订单查询工具，并将模型完整返回的 tool call 作为结构化结果交给运行协调器；现有客户端正文 delta 仅转发最终生成回合。协调器校验工具名、参数对象、JSON 格式、必需字段和大小，执行订单查询后按 OpenAI Chat Completions 协议把模型 assistant tool-call 消息及 tool result 追加到当前上下文，再发起最后一次流式模型调用。

每条用户消息只执行一次工具。第二个、未知或格式无效的工具请求以稳定依赖错误结束。工具查询必须受本次已有 deadline、取消和资源限制约束。只有尚未向客户端发送正文时，现有有限重试规则才可应用；工具查询结果在模型重试期间复用，不重复查询。

### RAG 无匹配时继续原问题的模型回合

RAG 检索成功但无可用片段时，将空 sources 和未改写的用户原问题交给 Agent 模型，允许订单工具调用。不得把“资料不足”硬编码成最终回答。检索错误、超时和取消路径不改变，不会继续到工具或生成调用。存在片段时仍按现有预算与 `withEvidence` 规则组装上下文，工具能力可与资料回答在同一轮并存。

### 用 MySQL JSON 列记录最小工具摘要

新增 Flyway 迁移在 `chat_message` 增加可空 `tool_calls_json JSON`。完成消息将至多一条摘要（固定工具名和非敏感成功状态）与正文、sources、用量和运行权释放在同一个终态事务中保存。参数、订单号、原始订单响应、地址和联系方式不写入摘要。历史 API 对旧行、用户消息、失败或空列返回 `toolCalls: []`。SSE done 使用同一已保存摘要。

不新建工具调用明细表：本期严格限制为每轮一个调用，摘要只作为聊天完成结果展示，不需要单独搜索、重试或审计工具参数。未来如要存多个调用的完整执行审计，应另立需求评估。

### API 契约只扩展完成摘要

不新增 HTTP 路径或请求字段。现有消息 SSE 仍是 `start/token/done/error`；只有成功 done data 新增 `toolCalls` 数组。历史 `ChatMessage` 新增相同字段；无调用返回空数组。请求及失败事件不返回 tool arguments 或内部异常。

## Risks / Trade-offs

- [兼容网关可能不支持 OpenAI 工具协议或流式 tool-call 响应] → 仅在声明的兼容协议能力下发送工具定义；协议错误走现有依赖错误，并用本地 HTTP 协议测试覆盖工具请求与结果回传。
- [模型可能编造或畸形地产生订单号] → 工具参数严格解析、限制长度和字段；订单查询仍由领域服务做租户及本人授权，任何不匹配均不可见。
- [模型最终回答可能错误解释订单数据] → 系统仅传回有限订单详情并要求依据工具结果作答；工具摘要仅表明调用事实，不作为回答正确性的证明。
- [新 JSON 列及 DTO 字段影响历史映射和 OpenAPI] → 列可空且旧记录映射空数组；Flyway 升级测试、聊天历史与 OpenAPI 契约测试覆盖回滚兼容性。
- [额外模型往返增加延时和费用] → 单轮最多查询一次并最多执行一次工具后续生成，共享既有总 deadline；超时沿用现有终态及释放运行权机制。

## Migration Plan

1. 新增向前兼容的 Flyway 迁移，在 `chat_message` 添加可空 JSON 摘要列；不修改已发布迁移或旧记录。
2. 部署支持新列读取和写入的应用；历史旧行返回 `toolCalls: []`。无需启用 RabbitMQ、Redis ChatMemory 或新基础设施。
3. 若需回退应用，旧版本可忽略新增列；不回退或删除已应用的 Flyway 迁移。

## Open Questions

无。工具范围、调用次数、API 形态及存储策略已在规格和本设计中确定。
