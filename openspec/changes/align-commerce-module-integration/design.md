# Design

## Context

动机见 `proposal.md`。本次约束以用户确认及 `api/docs/architecture/module-roadmap.md` 第 2–5、8 节为准：整合已交付模块；订单、物流继续只读；RAG、Function Calling、RabbitMQ 文档任务与 ChatMemory 后续独立实现。

已核对的现状：

| 位置 | 当前情况 | 本次处理 |
| --- | --- | --- |
| `db/migration/` | V5 会话、V6 物流、V7 订单、V8 库存、V9 商品 | V1–V5 不动，重排尚未执行的 V6–V9 |
| `db/devdata/` | R010 租户、R020 账号、R030 会话、R040 物流、R050 订单、R060 商品 | 保留 010–030，商品 → 库存 → 订单 → 物流 |
| 商品演示目录 | 商品 `2500000000000201–206`、SKU `2500000000000301–309` | 作为 dev 商品/SKU 权威标识 |
| 订单演示项 | 使用 `2100000000000901–916` 的占位商品/SKU，目录中不存在 | 映射至同商户真实商品/SKU，保留订单和订单项 ID |
| 库存 | 无 dev seed，fixture 只引用占位 SKU；调整只更新已有库存 | 增加真实 SKU 种子、校验及已有调整入口的首次初始化语义 |
| 库存主键（本次新增决策） | 三表 AUTO_INCREMENT；库存首次创建省略 id，流水与幂等 Mapper 使用 generated keys | 三表统一接现有 IdGenerator，运行时显式写入雪花 ID，种子/fixture 显式写入固定 ID |
| `ShipmentQueryService` | 找到运单就返回；无运单才检查订单访问权 | 所有 REST 分支先授权 |
| `OrderBackedOrderAccessGuard` | 直接调用订单 Mapper | 经订单域只读服务授权 |
| 商品公开查询 | 目录缓存没有库存维度，没有调用库存服务 | 缓存目录，响应阶段组合实时库存布尔值 |
| 商品公开路径 | `/api/v1/public/stores/{merchantCode}/...` 与认证的 storeSlug 命名及公开资源示例不统一 | 统一 `/api/v1/stores/{storeSlug}/...`，同步精确匿名 GET 白名单及契约 |
| `DevSeedUpgrade` / 迁移测试 | 存在 V8 和五份 R 的硬编码，遗漏当前商品迁移 | 按新清单更新精确白名单与断言 |

当前本地 Docker Desktop 的 dev 库只执行到 V5，这是用户提供的兼容基线，尚未在本工作流访问或修改数据库。本 change 不处理其他库的旧 V6–V9 升级。执行前仍需只读确认目标确实匹配该前提，防止意外连接错误实例。

主规范已经要求版本不可变、主体可信、数据分层及历史快照稳定。尚未归档的商品/订单/物流 change 记录的是各自交付语义；其中物流规范要求迁移晚于订单，而实际当前 V6 早于 V7；各模块文档和 seed 注册也残留旧编号。本 change 以新增跨模块契约协调这些差异，不修改其他 change 的完成状态或历史验收记录；实施时更新当前模块文档与交付交叉引用，既有功能要求继续适用。

## Goals / Non-Goals

**Goals:**

- 在数据层表达同租户父子关系，在服务层执行状态/归属/权限校验，两层职责分别验证。
- 从空库和原 V5 dev 基线迁移到相同 V9 结构，随后普通 dev 启动可重复执行且保留人工数据。
- 让未来只读 Tool 可复用真实领域服务；不要求先建设 Agent 工具才能验收模块联调。
- 在综合验收及本地升级前统一库存三表的应用分配雪花主键，沿用多个单体应用副本共享 MySQL 的部署目标，为不同实例配置不同 workerId。

**Non-Goals:**

- 不新增下单、支付、取消、退款、发货写接口或自动交易库存流程；不将查询订单变为库存变更入口。
- 不挪动已执行的 V5 会话表，不提前建立 RAG、Function Calling 或其他未来模块的表、队列、运行时和依赖。
- 不重构全部库存幂等框架或旧餐饮模块；库存主键按决策 8 统一，数量计算、乐观锁、幂等键范围和成功重放规则保持原约定。
- 不为已经执行旧 V6–V9 的其他数据库设计兼容修复，不执行生产操作。
- 不在本 change 实施真实 Nginx 集群、分库独立写入、跨库合并或自动 worker 租约；不借主键统一提前建设 RAG、Function Calling、RabbitMQ 文档任务或 Redis ChatMemory。

## Decisions

### 1. 冻结 V1–V5，只重排当前 dev 尚未执行的结构和种子

| 当前脚本 | 目标脚本 |
| --- | --- |
| `V9__product_module.sql` | `V6__product_module.sql` |
| `V8__inventory_tables.sql` | `V7__inventory_tables.sql` |
| `V7__order_tables.sql` | `V8__order_tables.sql` |
| `V6__shipment_tables.sql` | `V9__shipment_tables.sql` |
| `R__060_product_demo.sql` | `R__040_product_demo.sql` |
| 无库存演示种子 | `R__050_inventory_demo.sql` |
| `R__050_order_demo_orders.sql` | `R__060_order_demo_orders.sql` |
| `R__040_shipment_demo_data.sql` | `R__070_shipment_demo_data.sql` |

Flyway 先执行所有 pending V，再按 R 的描述排序；V 只放结构 DDL、不读取 R 数据。R010/020/030 保持名称与内容不变，后续 040/050/060/070 依次表达目录、库存、订单、物流的初始化依赖。会话结构与种子不依赖商品关系，没有必要移动 V5/R030。

选择重排是因为唯一需要保留的 dev 库尚未执行 V6–V9。追加 V10 的兼容路线不能满足用户希望首次创建也遵守业务依赖的目标；重写 V5 或伪造 history 则会破坏已执行版本的校验。其他数据库兼容不在本次范围。

### 2. 用同租户复合外键保障引用，服务继续执行业务规则

结构在对应尚未执行的迁移内一次建好：

- `inventory(merchant_id, sku_id)`、`inventory_transaction(merchant_id, sku_id)` 引用 `product_sku(merchant_id, id)`。
- 为 `product_sku` 增加唯一键 `(merchant_id, product_id, id)`，让 `trade_order_item(merchant_id, product_id, sku_id)` 引用这个整体，既防跨租户，也防把同商户的商品 A 与商品 B 的 SKU 拼在一起。
- `shipment(merchant_id, order_id)` 引用 `trade_order(merchant_id, id)`；`shipment` 增加 `(merchant_id, id)` 唯一键，供 `shipment_track(merchant_id, shipment_id)` 引用。
- 保留已有商品、订单与账号的同租户约束；新增外键使用 RESTRICT 语义，不级联删除、更新快照或库存流水。
- `shipment.order_no` 继续为履约快照；服务以授权后的 orderId 定位运单，种子 guard 同时核对其 order_no 与真实订单一致。库存 `biz_id` 仍为可空业务追溯字段，不在库存先于订单创建时加指向订单的外键，也不赋予其驱动交易状态的语义。

不采用只对全局 ID 加外键的方式，因为这不能约束商户与 SKU 所属商品。也不依赖外键判断商品上下架、库存数量或消费者归属：这些规则必须在 Service 中执行。

订单项继续保存独立成交快照，不在查询时 JOIN 当前商品重建历史。当前商品模块没有物理删除能力；未来如引入硬删除或目录归档，须另行设计历史引用保留方案，而不能解除本次约束后静默丢失关联。

### 3. 用职责分离的服务消除互相注入和跨域 Mapper 访问

以下为计划使用的服务职责，可沿现有包组织实现，不机械创建接口/impl：

| 提供方能力 | 调用方 | 返回/职责 |
| --- | --- | --- |
| 商品目录只读引用校验（如 `ProductReferenceService`） | 库存操作服务 | 按可信 merchantId 查 SKU 所属商品和 SKU 状态；不依赖库存或公开商品聚合 |
| 库存只读可售查询（如 `InventoryAvailabilityQueryService`） | 商品公开聚合、后续只读 Tool | 按 merchantId + SKU 返回布尔，支持一批 SKU；不回调商品服务 |
| 订单访问与定位（扩展 `OrderQueryService`） | 物流适配器/服务 | Actor 授权后返回 orderId/orderNo；提供独立服务间商户范围定位能力 |
| 原库存操作服务 | 现有员工库存入口 | 商品引用校验、幂等协调、事务重试与流水 |

商品聚合 → 库存只读，库存操作 → 商品引用校验；两个底层只读能力各自只依赖本域 Mapper，因此不会形成商品聚合 ↔ 库存操作的 Spring 构造依赖环。跨域调用不走进程内 HTTP，不访问提供方 Mapper，不构造虚假消费者 Actor；所有查询仍带 merchant_id。

### 4. 库存校验与首次初始化复用现有员工调整入口

- 操作前检查员工身份与可信商户，通过商品目录服务查真实 SKU。不存在/跨商户统一返回 404/13001，未认证/角色限制继续遵守现有安全链。
- 员工维护允许为本商户 DRAFT/UNPUBLISHED 商品下的 ACTIVE SKU 备货，商品未发布不等于 SKU 不存在。停售 SKU 不允许新建可售库存、正向调增或新增预占；停售后的已有库存可负向盘亏、释放/扣减已有预占，保持收尾操作可用。状态冲突使用 409 与新增库存码 13008，并登记文档。
- 已有正向 `adjust` 对缺失库存行时，在库存事务内从 0 初始化再按 delta 写库存与流水；负向缺失或其他无基础库存操作仍返回 13001。使用 `(merchant_id,sku_id)` 唯一键处理并发首次创建，重复请求保持原幂等语义，不增加初始化 HTTP 路由。
- 保持可售量/预占量、版本冲突重试、流水原子性和幂等成功重放语义；身份/目录校验不能被重复幂等键绕过。库存读接口不应因跨域聚合暴露员工精确库存给匿名主体。

这比要求仅靠 dev seed 创建所有新 SKU 的库存更完整，也比新增独立库存初始化业务模块更贴近现有维护功能。它不创建订单、不更改订单状态。

### 5. 商品公开查询统一店铺入口，在目录缓存之外组合实时库存

以已归档 `2026-11-06-add-redis-auth-sessions` 的公开店铺定位规则为依据，将商品公开入口统一为以下三个匿名 GET 路径：

- `/api/v1/stores/{storeSlug}/products`
- `/api/v1/stores/{storeSlug}/products/{productId}`
- `/api/v1/stores/{storeSlug}/skus/{skuId}`

原 `/api/v1/public/stores/{merchantCode}/...` 路径由本 change 替代，不保留兼容别名。认证归档中的商品路径原为未来资源示例，本次将其落实为商品查询的正式契约；不修改该归档或其他 change 的完成状态、历史验收记录。同步公开 Controller、查询服务、店铺定位缓存的参数命名以及当前文档、OpenAPI、后端契约测试和调用示例。按用户职责范围，前端代码不修改；只读核对其商品/SKU 地址，将差异记录为队友接入事项。

storeSlug 表达公开店铺定位符，初期复用商家编码，沿用认证的编码解析规则和 ACTIVE 商户要求；未知、停用店铺及不可见/跨店商品仍采用现有公开 404 语义。数据库继续保留 `merchant_code`，员工登录及 SOAP 继续使用 merchantCode，内部关联与租户隔离继续使用 merchantId；不新增 slug 字段或迁移数据，也不在本次引入子域名、HttpOnly Cookie 或独立可改名 slug。

匿名访问由安全规则决定，不由 `/public` 字面前缀决定。将原 `/api/v1/public/**` GET 放行改为仅精确匹配上述三个资源路径，不宽泛放行 `/api/v1/stores/**`；保留现有短信和消费者登录 POST 白名单。公开商品请求按 URL 店铺定位，即使携带无效或其他店铺 token 也不采纳身份、不认证或续期会话；其他店铺资源及商品维护写操作继续按原认证/角色规则处理。

在公开列表/商品详情包含的 SKU 以及公开 SKU 详情上增加布尔 `inStock`。先按现有店铺、PUBLISHED 商品、ACTIVE SKU 规则过滤，再调用库存只读服务；缺行或 available_qty=0 返回 false。消费者读取精确数量的权限不因该字段增加而扩大；员工库存接口保留原响应。

Redis 只缓存目录事实。缓存命中后仍批量读取当前请求需要的 SKU 库存并构造新响应，不把 `inStock` 长期写进缓存条目；升级时用目录缓存格式命名空间版本使旧条目自然失效。避免通过仅在库存写时失效所有商品缓存来维持一致性，也避免依赖 15 分钟目录 TTL 提供实时库存。

数据库查询失败返回既有存储失败语义，不伪装成无货；Redis 缓存故障仍按现有规则回源。修改并导出 OpenAPI；`inStock` 字段本身是兼容性扩展，去掉 `/public` 则是实际路由变更，调用方必须同步使用新路径。

### 6. 物流必须先经订单服务授权，包括已经有运单的分支

REST：`ShipmentQueryService.getForActor` 首先调用订单域访问服务；消费者按 merchantId+accountId、员工按 merchantId 查真实订单。授权失败统一 404/10004，之后才查询 shipment 和 tracks。`OrderBackedOrderAccessGuard` 改为服务适配器，删除其对订单 Mapper 的依赖。不得因为运单存在而跳过授权。

SOAP：保留现有服务间 token 信任域；merchantCode 解析后，经订单域服务在该商户内解析 orderNo，再按真实 orderId 读取物流。真实订单无运单返回 NOT_SHIPPED；未知订单/无效凭证仍为 Fault。服务凭证不进入前端，也不把 SOAP 的服务授权转成消费者授权。

订单详情查询不调用库存操作，也不要求商品当前可见；物流查询不推进订单履约状态。多轮记忆、HTTP 参数、SOAP 定位参数中的标识都不构成资源访问授权。

dev 继续使用现有目录 ID，稳定订单 `2100000000000301–307`、订单项 `2100000000000311–318` 和现有运单 ID 不变；将占位商品/SKU 引用统一重映射：

| --- | --- | --- | --- |
| 0311 | 2500000000000201 | 2500000000000301 | 国标充电器 |
| 0312 | 2500000000000202 | 2500000000000304 | 1m 黑色数据线 |
| 0313 | 2500000000000203 | 2500000000000308 | 白色耳机 |
| 0314 | 2500000000000202 | 2500000000000306 | 2m 数据线 |
| 0315 | 2500000000000201 | 2500000000000302 | 欧标充电器 |
| 0316 | 2500000000000202 | 2500000000000305 | 1m 白色数据线 |
| 0317 | 2500000000000203 | 2500000000000307 | 黑色耳机 |

首次生成的快照名称/规格使用对应 SKU 的合理成交含义，成交价可与现价不同；保留并核对已有演示订单总额与订单项金额加总。此基线尚无旧业务订单，不执行对已存在真实订单的 UPDATE 映射。

R050 为上述目录 SKU 提供可售大于 0、等于 0、存在预占量和停售保留量样例，覆盖两个商户。库存种子只初始化缺失库存，不因重跑恢复/覆盖人工调整后的数量和 version，也不伪造已执行交易流水。R070 的隔离租户运输中运单对应订单须为 SHIPPED，修正当前 PENDING_SHIPMENT 与 IN_TRANSIT 演示状态不一致。

所有 R 在任何业务写入前检查父记录、固定 ID/自然键归属和商品/SKU 组合冲突；缺依赖明确失败，不使用 INSERT IGNORE 或静默 JOIN 漏插。重复执行仅补缺失；正常重启没有校验和变化时不重跑，显式补种保留人工修改。

test 的 `product_catalog.sql` 保持 `260...` 独立空间，订单/库存 fixture 改用该空间中的本租户 SKU，更新所有 `@Sql` 顺序为 auth → product → inventory/order → shipment，并按外键反向清理。补充有库存/缺货/停售和同租户他人已发货订单用例；不把 dev seed 当常规测试 fixture。

### 8. 库存三表统一复用现有雪花生成器，先于综合验证实施

此决策替代本 change 原先“保持现有库存主键”的范围限制。新增任务独立放在第 6 节；原综合验证与本地升级章节顺延为第 7、8 节。第 1–5 节保留已完成状态；新增验收单独记录，不把历史测试结果当作雪花改造已完成的证明。

**主键生成与写入：**

- 新 V7 的 `inventory.id`、`inventory_transaction.id`、`inventory_idempotent.id` 使用无默认值的 `BIGINT NOT NULL` 主键，移除 AUTO_INCREMENT；保留商户/SKU 唯一键、同商户外键和原业务索引。
- 运行时复用 Spring 管理的现有单例 `common.id.IdGenerator`。库存事务内首次创建库存及每条新流水、幂等服务创建新记录时，均在 INSERT 前由服务端分配 ID，Mapper 显式插入 id；删除 generated-key 回填，不由 Controller、客户端或 SQL 生成主键，也不为每张表另建雪花生成器。
- 并发首次创建仍由 `(merchant_id, sku_id)` 唯一键裁定；库存重试仍运行在新的事务内，重复成功幂等键不新增库存或流水，FAILED 抢回继续使用原幂等记录。事务失败或重复键竞争允许消耗但不落库的 ID，不要求连续或回收 ID；不能据主键连续性、数值大小或雪花顺序推断业务成功、提交先后或严格事件顺序。
- 生成器失败必须沿既有错误契约失败，不回退到自增、时间戳或本地计数；不得留下部分库存/流水提交或把本次失败标为 SUCCESS。

**演示和测试数据：**

R050 当前省略库存 id，必须改为显式固定 ID，并补齐固定 ID/自然键归属冲突检查。`inventory.sql`、所有相关测试中的直接 INSERT 和 Mapper 调用同步传入显式 ID，保留 dev/test 独立固定 ID 空间，不修改目录、订单或物流已有标识。固定 seed/fixture ID 是可复现数据的例外，不在 SQL 中实现雪花，也不改写既有真实记录的主键；受控重复执行只补缺失，保留人工数量/version，不伪造流水。断言按商户和稳定业务标识定位，不依赖表空、自增起点、连续性或 ID 位数。

**多实例部署与后续模块：**

同一份单体应用可启动多个副本，由 Nginx 分发请求，共享 MySQL、Redis 等中间件。共享 MySQL 时自增本来也可唯一；本次选择雪花是统一新业务约定，不能把换主键等同于完成集群验收。每个同时存活的副本（包括滚动发布的新旧实例）必须分别配置不同的 `MERCHANT_ID_WORKER_ID`，并在实例内共享同一 IdGenerator。沿用既有 epoch、worker 范围、时钟回退/序列耗尽及重启复用规则，不复制默认 worker 0 扩容，不引入第二套生成算法。

后续文档、切片、异步任务和会话等新业务记录沿用现有应用分配 ID 约定，各有自己的领域标识；库存查询仍按可信 merchantId+skuId 调用 Service。全局主键不能替代租户过滤、Actor 授权、业务幂等键或 MQ 去重，当前没有跨域引用裸 inventory.id 的需要。

**迁移范围：**

只面向新库及本 change 已约定尚在 V5、未应用 V6–V9 的本地 dev 基线，在尚未执行的新 V7 内一次完成结构调整；不为此增加 V10，不修改 V1–V5 与 R010/020/030。隔离测试库由修订后的资源重新初始化。本地升级前仍必须只读复核 history；如目标已应用 V7 或不再符合 V5 假设，停止该目标的升级并另行评审向前迁移，不 repair、改 checksum/history、重编号现有记录或删除业务卷。

**验证：**

在隔离 MySQL 检查三表无 auto_increment、运行时实际保存了注入生成器分配的 ID；回归首次/并发初始化、乐观锁重试、流水原子回滚、成功重放、FAILED 重试及生成器故障。受控时钟下用不同 workerId 的生成器模拟不同实例，验证同一毫秒并发生成不重复；结合现有生成器的时钟回退和耗尽测试，不启动完整 Nginx 环境。第 7 节再覆盖空库/V5 升级、跨模块及全量 clean verify，第 8 节才执行本地 dev 升级。

## Risks / Trade-offs

- [本地 history 与 V5 前提不一致或存在未登记业务表] → 迁移前只读核对目标、history、checksums 和新表不存在；不匹配即停止，不用 repair 重新解释旧版本。
- [重排资源后旧 V/R 留在 `target/classes` 或旧包继续运行] → 发布/验收使用 clean 构建，检查 JAR 内唯一版本及 R 描述，停止同库旧后端后再升级。
- [外键使现有测试 fixture/清理失败] → 同步所有消费者、SKU、订单、运单 fixture 装载与反向清理，不靠关闭 FOREIGN_KEY_CHECKS 运行测试。
- [商品与库存双向业务依赖] → 分离目录引用校验和库存只读查询，用真实 Spring 上下文验证无依赖环。
- [停售后的库存无法清理] → 区分新增可售供应与收尾操作，不把公开可见性过滤直接复用于全部库存写入。
- [商品缓存使库存状态滞后] → 每次响应单独查已提交库存，不缓存库存布尔；使用批量查询避免每个 SKU 一次 SQL。
- [统一商品路径后匿名读取变 401，或店铺路径被过度放行] → Controller 与精确匿名 GET 匹配同步调整，验证无效/异店 token 不影响公开读取，未声明私有路径与写操作仍受保护；同步契约与调用地址，移除旧商品路径。
- [MySQL DDL 部分失败无法事务回滚] → 迁移前保留结构+数据备份并在隔离实例恢复核验；失败后保留诊断并停止，不删卷或清 history。
- [已存在其他库的旧 V6–V9] → 用户明确不要求兼容；当前工具遇到旧布局应拒绝，不为其实现自动改名 repair。
- [移除自增后遗漏某条 INSERT 或 seed/fixture] → 逐项核对三表所有写入点与 generated-key 配置，以隔离 MySQL、R050/fixture 和 clean verify 验证显式主键完整落库。
- [多实例错误复用同一雪花 worker，或生成失败后部分业务提交] → 沿用每实例独立 worker 与实例内单例生成器约束，验证不同 worker 并发、生成失败及事务回滚；雪花不代替业务唯一键和幂等。

## Migration Plan

1. 实施首先固定当前 V1–V5 与 R010/020/030 文件摘要，更新未执行 V/R、调用边界、fixture、维护工具和文档；先在隔离容器验收，不启动本地 dev 应用触发迁移。
2. 完成任务第 6 节的库存雪花改造：修订未执行的新 V7、运行时显式 ID 写入、R050/fixture、库存与多 worker 定向测试及文档；不连接或改写本地 dev 数据。
3. 执行任务第 7 节，验证空库路径及冻结原 V1–V5 的 V5 升级路径，比较最终结构与种子关联，包括三张库存表无自增与显式 ID；再次 migrate 应无操作，已有账号/会话/人工值及原 history 行保持原样。维护工具的精确文件、描述、版本和 repeatable 白名单同步新映射，现有旧 R 专用受控功能不得转变为自动 repair。
4. 执行任务第 8 节的本地实施前置步骤：先 `docker compose up -d --wait`，应用保持停止；只读确认 gba-dev/gba_dev 与 V5 基线，完成结构+数据备份并恢复核验。若已应用 V7 或其他新迁移导致目标不符，停止并另行评审；若存在旧名 R Missing，沿已有受控维护流程单独报告处理，不将其当本次 V6–V9 重排的默认步骤。
5. 使用 clean 构建结果在 IDEA 只激活 dev、工作目录 api、JDK 21；通过 dev_admin 自动执行新 V6–V9 和适用 R，保持 validate-on-migrate=true、clean-disabled=true、out-of-order=false、baseline-on-migrate=false。
6. 核对 Flyway validate、稳定 ID 关联、库存运行时雪花主键、两租户权限、商品库存布尔、订单快照和物流状态；二次启动 history 与业务值不变后，记录健康检查和断点调试入口的真实结果。
7. 失败即停后端并保留原 history/日志；按隔离演练结果选择受控恢复完整备份或另行评审向前修复。应用版本回退前验证数据库兼容性，不通过回滚代码自动降级数据库。

本工作流只生成上述规划；本地升级验收属于后续 apply，不在提案阶段执行。没有需要继续向用户确认的设计级范围问题。
